## Executive Summary

Loom is an **AI-powered coding agent** built in Rust that enables developers to interact with LLM-powered assistants capable of executing tools for file operations, shell commands, and code analysis. The system uses a **server-side LLM proxy architecture** where API keys never leave the server, with the CLI acting as "hands" (executing tools locally) while the server acts as "brain" (routing LLM requests). The codebase is organized as a Cargo workspace with 85+ crates following a modular, trait-based design.

---

## Architecture

### Purpose

Loom solves the problem of bridging LLM reasoning with concrete filesystem and shell operations while enforcing security boundaries. It's used by developers who want AI assistance for coding tasks with the ability to read files, edit code, run commands, and auto-commit changes.

### Entry Points

| Entry Point | Type | Purpose |
|-------------|------|---------|
| `loom-cli` | Binary | Interactive REPL, weaver management, ACP server |
| `loom-server` | Binary | HTTP API server with LLM proxy, auth, thread storage |
| `web/loom-web` | SvelteKit | Web frontend for thread viewing and management |
| `loom-tui-app` | Binary | Terminal UI (shell only, no agent integration yet) |

## Patterns

### Design Patterns in Use

| Pattern | Where Used | Example |
|---------|------------|---------|
| State Machine | Agent behavior | `AgentState` + `AgentEvent` → `AgentAction` |
| Registry | Tool management | `ToolRegistry` with `Box<dyn Tool>` |
| Proxy | LLM communication | `ProxyLlmClient` → Server → Provider |
| Trait Objects | Extensibility | `LlmClient`, `Tool`, `PostToolHook` traits |
| Builder | Request construction | `LlmRequest::new().with_messages().with_tools()` |
| SSE Streaming | Real-time responses | `LlmStream` with `LlmEvent` variants |

### Error Handling

Errors use a layered approach:
- **`thiserror`** for defining error enums with `#[error("...")]` messages
- **`anyhow`** for propagation with context via `.context("...")`
- **`Result<T>` type aliases** per crate (e.g., `type Result<T> = std::result::Result<T, LlmError>`)
- **HTTP responses** use `ErrorResponse { error: String, message: String }` JSON format
- **Secrets** use `loom-common-secret::Secret<T>` which auto-redacts in Debug/Display/tracing

### Async Model

- **Tokio runtime** for all async operations
- **`async-trait`** for async trait methods
- **SSE streaming** for LLM responses (server wraps provider events in `LlmStreamEvent`)
- **Sequential tool execution** in CLI (parallel-ready state machine, but not used)
- **No automatic reconnection** for dropped streams; relies on Agent retry mechanism

### Data Access

- **SQLite via sqlx** with compile-time query checking
- **Migrations** in `crates/loom-server/migrations/` as numbered SQL files
- **Thread storage** uses `loom-thread` crate with FTS5 full-text search
- **No ORM** - raw SQL queries with typed results

## Data Flow

### Core Entities

| Entity | Purpose | Key Fields |
|--------|---------|------------|
| Thread | Conversation container | `id`, `title`, `messages`, `version` |
| Message | Single turn in conversation | `role`, `content`, `tool_calls` |
| User | Authenticated user | `id`, `email`, `locale` |
| Organization | Multi-user container | `id`, `slug`, `members` |
| Weaver | Remote execution pod | `id`, `pod_name`, `status`, `owner_user_id` |

### Critical Paths

1. **User Input → LLM Response → Tool Execution**:
   ```
   stdin → Message::user() → LlmRequest → ProxyLlmClient
   → HTTP POST /proxy/anthropic/stream → LlmService → AnthropicClient
   → SSE stream → LlmEvent::TextDelta/Completed → execute_tool()
   → Message::tool() → loop back to LlmRequest
   ```

2. **Auto-Commit After Mutating Tools**:
   ```
   edit_file/bash completes → has_mutating_tools() check
   → PostToolsHook::run() → AutoCommitService → git add/commit
   → CommitResult returned to Agent
   ```

3. **Weaver Provisioning**:
   ```
   CLI: loom new → WeaverClient.create_weaver()
   → Server: /api/weaver POST → K8sProvisioner.create_pod()
   → Pod starts → SVID issued → WireGuard tunnel established
   → CLI: loom attach → WebSocket to pod
   ```

### Validation Boundaries

- **Input validation** at HTTP handler level (request parsing)
- **Authorization** via ABAC middleware before route handlers
- **Tool sandboxing** via `ToolContext.workspace_root` path restriction
- **Secret protection** via `Secret<T>` wrapper (never logged/serialized)

## Tricks & Gotchas

### For New Developers

1. **API keys are server-side only** - The CLI never has direct LLM provider access. All requests go through the proxy.

2. **Sequential tool execution is intentional** - The state machine supports parallelism, but CLI executes sequentially to avoid file race conditions. Don't enable parallel execution without adding file locks.

3. **The Agent state machine is passive** - It receives events and returns actions; it doesn't drive itself. The CLI/ACP must implement the event loop.

4. **Retry mechanism is currently dead code** - The `RetryTimeoutFired` event is never fired by any consumer. The Agent has retry logic, but no runtime uses it.

5. **Svelte 5 only** - The web frontend uses Svelte 5 runes (`$state`, `$derived`, `$effect`). Never use Svelte 4 patterns (`export let`, `$:`, `on:click`).

6. **cargo2nix for builds** - After modifying `Cargo.toml`/`Cargo.lock`, run `cargo2nix-update` to regenerate `Cargo.nix`. This is required for migrations too (they use `include_str!`).

### Performance Considerations

- **SSE streaming** avoids buffering entire LLM responses
- **FTS5 search** for thread content (fast full-text queries)
- **Connection pooling** via `loom-common-http::new_client()`
- **No parallel tool execution** yet (potential optimization)

### Debugging Tips

- **LLM issues**: Check both client-side (`ProxyLlmClient` logs) and server-side (`llm_proxy.rs` logs)
- **SSE debugging**: Inspect raw HTTP traffic to see exact events
- **Tool failures**: Look for `ToolError` in CLI output; tools log to tracing
- **Weaver issues**: `kubectl get pods -n loom-weavers` and `kubectl describe pod`

### Known Workarounds

| Workaround | Why It Exists | Location |
|------------|---------------|----------|
| Hardcoded `MUTATING_TOOLS` list | No `is_mutating()` trait method yet | `agent.rs:48-63` |
| Manual event loops in CLI/ACP | No shared `AgentRuntime` abstraction | `main.rs`, `agent.rs` |
| Raw JSON error display | No `parse_error_response()` helper | `client.rs:148-150` |
| `retry_after_secs: None` always | Header parsing not implemented | `client.rs:143-145` |
